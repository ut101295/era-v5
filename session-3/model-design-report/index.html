00 Thesis

Frontier quality for India is not a translation problem — it is a data-allocation and tokenizer problem. Generic multilingual models spend 4–11 tokens per Indic word[1] and starve Indian context in the mix. Bharat‑40B fixes both: a 40B dense model trained on ~16T tokens with a deliberately India‑weighted mix, cleaned with a per‑language quality pipeline, evaluated on Indic + code + agentic axes, and served through a 262,144‑entry tokenizer whose vocabulary is re‑allocated from CJK toward Brahmic scripts + code — the same size as Gemma 3, but pointed at India.

01 Language & capability scope

We treat code as a first-class language and tier natural languages by speakers × digital text availability × script family, so vocabulary and data budget follow demand, not vanity coverage.

TierLanguagesScript familyWhy
AnchorEnglish, codeLatinReasoning backbone, coding/agentic transfer, global knowledge
T1Hindi, Bengali, Marathi, Telugu, TamilDevanagari · Bengali · Dravidian~700M+ speakers; largest native digital corpora
T2Gujarati, Kannada, Malayalam, Odia, PunjabiBrahmicStrong regional demand; moderate corpora
T3Assamese, Urdu, + Hinglish / romanizedBrahmic · Perso‑Arabic · LatinLow‑resource + code‑mixed reality of Indian chat
India‑first ≠ Indic‑only. The model must reason in English and code at Gemma‑3 level; "India‑first" is a worldview — Indian law, civic systems (UPI, Aadhaar, IRCTC), history, and cultural defaults — layered on a strong global base, not a monolingual silo.

02 Data strategy — what we collect & why

Only Llama 3 publishes an explicit mix (~50% general / 25% math+reasoning / 17% code / 8% multilingual over ~15T)[2]. We start there and re-weight for India: multilingual is a floor to smash, code/math held high.

The scarcity reality. Native high-quality Indic web text is tiny vs a 16T budget — Sangraha‑Verified ≈ 64B, IndicCorp v2 ≈ 20.9B tokens, and severely skewed (Hindi 1.86B vs Assamese 32.6M — a ~57× gap)[6][7]. Reaching 3.5T Indic tokens means controlled upsampling (≈3–5 epochs on verified native text) + high‑quality translation (IndicTrans2) + OCR/ASR harvesting — never brute synthetic. Sangraha is ~65% synthetic; we cap synthetic share and prefer native, since over‑epoching risks memorization and synthetic dilutes quality[5].

Curriculum, not a static pour

Proportions shift during training (Llama 3 upsamples math, raises non‑English late)[2]. We run 4 phases: English/code foundation → introduce T1 Indic + math → T2/T3 low‑resource upweight → joint consolidation (final ~10% of steps, all languages) to fight catastrophic forgetting[8].

Post-training — SFT

  • Indic instructions: native-authored (bhasha) + verified-translated + Hinglish/code‑mixed (real Indian chat)
  • Coding: instruction→code, bug‑fix, repo‑level multi‑file, code review
  • Agentic: function‑calling, multi‑step tool use, terminal/computer‑use, ReAct trajectories
  • Reasoning: verified CoT + R1‑style distilled traces from a strong teacher[9]
  • India‑domain: UPI/IRCTC/legal/agri/health task scenarios

RL / Alignment

  • GRPO (no value model, no DPO required) — the DeepSeek‑V3 template[9]
  • Verifiable rewards: unit tests (code), answer‑checkers (math), execution success (tools) → RLVR
  • Model-based rewards for free‑form & Indic fluency, with native-speaker preference data
  • Constitutional / India‑first: constitutional values, multi‑religion/caste/region sensitivity, refusal calibration for Indian legal context

03 Data cleaning pipeline

One backbone pipeline, tuned per objective. Order matters: identify → dedup (carefully) → quality‑filter → safety → decontaminate → weight.

1 · Language IDfastText / IndicLID per script; drop misidentified
2 · DedupURL→doc→line + MinHash (5‑grams, 112 hashes, 14×8, 75%)[4]
3 · QualityFineWeb‑Edu‑style classifier, trained per language
4 · Heuristicsline‑freq >6×, symbol ratios, script purity
5 · Safety/PIIPII redaction, unsafe/CSAM filters
6 · Decontaminaten‑gram overlap vs all eval sets
Dedup less, not more, for Indic. FineWeb found per‑snapshot dedup matched RefinedWeb while global dedup gave only modest uplift and removed up to 90% of older data — the removed text was better than what stayed[4]. For scarce Indic data, aggressive global dedup would strip irreplaceable text, so we default to per‑source dedup + conservative global near‑dup.

Quality filter, built for India

Replicate FineWeb‑Edu: a strong LLM scores ~500K samples 0–5, train a cheap embedding‑regressor, classify the whole corpus (~6K H100‑hrs)[4]. Train one classifier per Indic language so English‑centric "quality" doesn't down‑rank valid Indian English / regional content.

Per-objective specifics

Code: AST‑parse/compile filter, license filter, drop minified/autogen. Math: symbolic answer‑verification, keep step‑by‑step. Indic: Unicode NFC normalization + script‑purity + MT‑artifact removal in synthetic; explicit romanization handling for Hinglish.

The NFC + script-aware handling requirement is the same lesson our Session‑2 tokenizer surfaced: naive splitting shatters Indic matras and wrecks compression.

The gap we fill — IndiaBench. No standard Indic coding or agentic benchmark exists. We propose: IndiaBench‑Code (HumanEval/MBPP tasks with Indic‑language prompts & docstrings) and IndiaBench‑Agent (Indian‑context tool‑use — UPI payments, IRCTC booking, DigiLocker, govt portals — a BFCL‑style function suite in Hindi + English). 05 Fertility targets → tokenizer size

Fertility = tokens per word; lower is faster + cheaper + longer effective context. Generic tokenizers are catastrophic on Indic (Llama‑3 / Qwen produce 8–11 tokens/word on Telugu; Sarvam‑1's Indic vocab gets 1.4–2.1)[1]. We set targets first, then size the vocabulary to hit them.

Dravidian scripts are agglutinative → intrinsically higher fertility even with a good tokenizer; the target is "near‑native‑tokenizer," not parity with English.

Step 2 — allocate the vocabulary budget

Fertility falls as we give a script more merges — but with diminishing returns; IndicSuperTokenizer shows pre‑tokenization matters more than raw size and gains plateau past ~200K[12]. So we allocate deliberately across scripts and stop at a power‑of‑two boundary.

Decision: 262,144 tokens (2¹⁸)

Same footprint as Gemma 3, but the budget is re‑pointed from CJK to Brahmic scripts + code. Buckets sum exactly to 262,144.

Why this number — and not the alternatives

OptionVerdictReason
128K (Llama 3)Too small12+ Brahmic scripts + code + English can't coexist; Indic fertility stays 2.5–4×
262,144 (2¹⁸)ChosenHits fertility targets; embedding cost ~5% of params at 40B — effectively free[3]
>300KDiminishingGains plateau past ~200K[12]; low‑resource rows rarely activate → wasted params + softmax cost
Per-language tokenizersRejectedBreaks cross‑lingual transfer & code‑mixed (Hinglish) input; one shared vocab is required
Why the cost is negligible: in Gemma 3 the 262K embedding table is ~30% of the 1B model but only ~5% of the 27B model[3]. At 40B it's ~4% — a rounding error against the compute saved by halving Indic sequence lengths every forward pass, for the model's entire life.
